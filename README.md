## boxysean.com

The source of this site is in [jekyll/](jekyll/): Jekyll, `permalink: pretty`, with the
blog and portfolio as post collections. Everything else in `jekyll/` is `media/`
(stylesheets, JS, images) and the shared layouts in `_layouts` / `_includes`.

### Where it runs

| | before | after |
|---|---|---|
| Build | `docker run jekyll/jekyll jekyll build` (Makefile), or `jekyll build` (deploy.sh) | `bundle exec jekyll build` with the committed `Gemfile.lock` |
| Host | AWS S3 bucket `s3://boxysean.com/`, synced with `aws s3 sync` | Netlify, configured by `netlify.toml` |
| Default branch | `master` | `master` |

`deploy.sh` and the old `make deploy` S3 sync are the legacy path; `make deploy` now
deploys to Netlify. The S3 sync is retired once DNS points at Netlify (see the hosting
issue).

### Local development

Ruby 3.2 and Bundler are the only requirements; the docker image is no longer needed.

    bundle install          # or: make install
    make serve              # http://localhost:4000, live reload

If Ruby is the system package (Debian/Ubuntu, gems under `/var/lib/gems`), Bundler
cannot write there as a normal user. Install into the checkout instead — the
`Makefile`'s `bundle exec` picks it up automatically:

    bundle config set --local path vendor/bundle
    bundle install

### Build

    make build              # -> jekyll/_site

`make build` is exactly the command Netlify runs
(`bundle exec jekyll build --source jekyll --destination jekyll/_site`), so a green
`make build` from a clean checkout means the site will build on the host.

### Deploy

Netlify is linked to this GitHub repo: pushes to `master` build production. Site:
`boxysean-com` (`https://boxysean-com.netlify.app`, site id
`94501faa-3611-49ea-b8ec-537ce1326bc1`). The custom domain is attached in phase 2 once
DNS is re-pointed.

**Deploy previews do not build yet.** The site's setting is on (`build_settings.skip_prs`
is `false`) and `netlify.toml` carries a `[context.deploy-preview]` command, but Netlify
receives no build events for anything except `master`. Verified on 2026-10-26 three ways:
opening PR #15, pushing twice to its branch, and widening `allowed_branches` from
`["master"]` to all branches — zero deploys and zero Netlify commit statuses resulted, and
only the three `master` pushes ever produced a build. Widen-then-restore left the site
config as it was.

The missing piece is the GitHub side of Netlify's integration, not the repo: in the Netlify
UI, *Site settings → Build & deploy → Repository* needs the Netlify GitHub App re-linked /
re-authorised for `boxysean/boxysean.com` so `pull_request` and non-default-branch `push`
events are delivered. That needs account-owner access; the automation token cannot read or
write repo webhooks (GitHub returns 403). Once that is done, `netlify deploy` from CI or a
re-open of any PR will produce a preview with no change to this repo.

Until then, verify a branch before merging with `make build` and
`make deploy-preview`, which uploads a draft deploy and prints its URL without touching
production.

For a manual deploy from a checkout (hotfix, or before the link existed), use the
Netlify CLI authenticated with the token in 1Password ("Netlify API token"). No
`netlify link` is needed — the `Makefile` pins the site id:

    export NETLIFY_AUTH_TOKEN=$(op read "op://Shared with CoreyChimpBot/Netlify API token/password")
    make deploy             # production deploy of jekyll/_site
    make deploy-preview     # throwaway deploy URL, no production impact

`NETLIFY_SITE_ID` overrides the site the deploy targets. Always deploy through
`make`: a bare `netlify deploy` from an unlinked checkout has no site to publish
to and creates a brand-new one (that is how a stray `idyllic-…` site appeared on
2026-10-26).

### Rollback

Netlify keeps every deploy. In the Netlify UI open the site, go to *Deploys*, pick the
last known-good deploy and choose *Publish deploy*. That republishes those exact files
without a rebuild, in seconds. For a code-level rollback, revert the commit and push to
`master`.

### Changing the gems

`Gemfile.lock` is committed and pins the toolchain (Jekyll 4.4.1, Ruby 3.2). To
upgrade, edit `Gemfile`, run `bundle update <gem>`, and commit both files.
